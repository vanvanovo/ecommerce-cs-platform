## 三、设计要点

1. **参数化工具、无 SQL 直通**：工具只暴露固定参数（订单号/手机号/SKU），模型只负责"选工具+填参数"，注入面从根上消除（与办公助手 SQL 白名单同一思想）。
2. **统一返回协议**：`status ∈ success / not_found / invalid / rejected / duplicate`，上层 Agent 可编程处理，不用解析自由文本。
3. **写操作三重保障**：幂等键（idempotency_key）+ 唯一部分索引（并发竞态时回查已存在工单）+ 审计日志（谁在什么时候对哪个单做了什么）。
4. **规则引擎与《售后政策》同一口径**：7 天窗口 / 拆封例外 / 金额 ≥ 500 转审批 / 保修状态；`quality_path` 明确区分"无理由退货"与"质量问题保修"两条路。
5. **复用既有 MCP 架构**：FastMCP stateless + streamable-http，挂载为主应用子路由——和知识库/联网搜索 MCP 是同一扩展位，新增工具不影响主链路。

## 七、追加：MCP 服务间鉴权（X-MCP-Key）

> 2026-10-04 追加 ｜ commit `78b163c` ｜ 验收 **13/13**（11 功能 + 2 鉴权）

**实现**

| 项 | 说明 |
|---|---|
| 中间件 | `backend/mcp/auth.py` → `ApiKeyAuthMiddleware`（ASGI，校验 `X-MCP-Key`） |
| 开关 | `MCP_API_KEY` 未配置时放行（本地开发）；配置后强制 401（JSON-RPC 风格错误体） |
| 范围 | 仅包裹 `/mcp/cs`（含客户 PII + 写操作）；kb / web-search 保持本地开放，P6 可一键统一 |
| 客户端 | `client.py` 调用时自动附带 Key（服务间身份），业务代码零改动 |

**踩坑记录**：`app.mount` 的子应用不共享父应用中间件 → 鉴权必须包在子应用**外层**；但包装后 `lifespan_context` 要用**原始 FastMCP 子应用**驱动（`ApiKeyAuthMiddleware` 没有 `.router`）——已在 `main.py` 用 `_cs_mcp_app`（原始）/ `_cs_app`（鉴权包装）两个引用解决。

**验收结果**：无 Key → 401；错误 Key → 401；带 Key → 11 项功能全过。

**为什么这样设计**：三层身份分层——用户 → 业务 API 用 JWT；平台 → MCP 工具层用 API Key（服务间身份）；第三方 → Webhook 用平台签名。终端消费者**永远拿不到 MCP Key**，只能通过对话入口让 Agent 去调工具，杜绝"自己给自己发补偿券"。
