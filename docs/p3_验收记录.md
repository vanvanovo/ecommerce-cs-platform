## 四、设计要点

1. **四种范式各司其职**：商品咨询=RAG 图、订单物流=槽位状态机、售后=规则+HitL、投诉=规则风险扫描+LLM 话术——**不是所有 Agent 都硬套 ReAct**，按业务特性选范式。
2. **HitL 全链路**：`interrupt` 暂停 → 主管查看审批材料 → `Command(resume)` 恢复 → 工单落定（approved/rejected）→ 审计留痕；权限隔离（仅 teacher/admin，普通用户 403）。
3. **规则与 LLM 分工**：高危词/负面词用确定性规则（零成本、可解释）；订单号/手机号用正则精确抽取（强格式槽位比 LLM 更准更便宜）；LLM 只负责话术生成与答复排版。
4. **转人工的两种形态**：投诉="交接包+升级"（不暂停，人机会话异步）；售后="审批暂停"（interrupt，需要主管决策）——按语义选机制，不滥用 interrupt。
5. **追问边界**：连续两次缺参自动转人工，杜绝无限追问。
6. **幂等贯穿**：售后建单幂等键含 session/工单类型，重复提交不重复建单。
7. **防骗赔红线**："签收未收到"先识别为物流异常件（查轨迹佐证）→ 转人工核实，再谈退款——这是真实客服系统里必要的风控边界。

## 五、遗留（转入 P4/P6）

- **统一入口切换**：四个 Agent 目前是独立接口（`/order`、`/aftersale`、`/complaint` + 统一入口问答），P4 由 Orchestrator 做标签换代与 SSE 统一路由；
- **Redis 分布式锁**：随 P6 接入 Redis 时一起做（当前写操作靠幂等键 + 唯一索引兜底）；
- 主管审批页 UI、工单池/未解决问题持久化（P4 转人工分支 + P6 前端）；
- MemorySaver 重启丢会话（P6 可选升级 Postgres checkpointer）。
